# Milestone 4 — Operational Event Persistence

---

## Overview

This milestone configures Alembic for the FleetGuard backend and delivers the
first production-quality database migration for the Operational Event Store.

The migration creates the `operational_events` table in PostgreSQL with correct
native types (UUID, JSONB, TIMESTAMP WITH TIME ZONE, named ENUMs) and a full
set of query-optimised indexes.

No business logic, repositories, or APIs were created.

---

## Objective

The `OperationalEvent` SQLAlchemy model introduced in the previous milestone
defined the Python-level structure but had no corresponding database schema.
This milestone bridges that gap by:

- Initialising and configuring Alembic for async SQLAlchemy.
- Producing a hand-crafted PostgreSQL migration that targets production-grade
  column types.
- Establishing the index strategy required for the downstream query patterns of
  the Event Processor, Fleet Memory, and Fleet Intelligence Engine.

## Database Changes

### Table: `operational_events`

| Column | PostgreSQL Type | Nullable | Notes |
|---|---|---|---|
| `id` | `UUID` | NO | PK, `gen_random_uuid()` default |
| `event_type` | `event_type` (ENUM) | NO | Named PG enum |
| `entity_type` | `entity_type` (ENUM) | NO | Named PG enum |
| `entity_id` | `VARCHAR(255)` | NO | Accepts any key format |
| `occurred_at` | `TIMESTAMP WITH TIME ZONE` | NO | Physical-world time |
| `recorded_at` | `TIMESTAMP WITH TIME ZONE` | NO | Default `NOW()` |
| `capture_method` | `capture_method` (ENUM) | NO | Named PG enum |
| `verification_status` | `verification_status` (ENUM) | NO | Default `'PENDING'` |
| `created_by` | `VARCHAR(255)` | YES | NULL for system events |
| `payload` | `JSONB` | YES | Event-specific data |
| `event_metadata` | `JSONB` | YES | Operational metadata |
| `notes` | `TEXT` | YES | Human annotation |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | NO | Default `NOW()` |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | NO | Default `NOW()` |

| Property | Value |
|---|---|

| File | `migrations/versions/001_operational_event_create_table.py` |

The migration is **hand-crafted** (not autogenerated) to guarantee correct
PostgreSQL types regardless of the local development database dialect (SQLite).

**Apply:**
```bash
alembic upgrade head
```

**Roll back:**
```bash
alembic downgrade -1
```

**Generate SQL preview (no live DB required):**
```bash
alembic upgrade head --sql
```

## Architecture

This milestone sits at the **infrastructure layer** of the Event-Driven Architecture:

```
┌─────────────────────────────────────┐
│         Application Layer           │  ← models, schemas (Milestone 3)
│  OperationalEvent ORM model         │
│  Pydantic schemas                   │
└─────────────────┬───────────────────┘
                  │
┌─────────────────▼───────────────────┐
│        Infrastructure Layer         │  ← THIS milestone
│  Alembic (env.py + alembic.ini)     │
│  Migration 001                      │
│    - operational_events table       │
│    - 4 ENUM types                   │
│    - 8 indexes                      │
└─────────────────────────────────────┘
                  │
┌─────────────────▼───────────────────┐
│         PostgreSQL Database         │
└─────────────────────────────────────┘
```

Alembic reads `DATABASE_URL` from the application's pydantic-settings config
at runtime — no credentials are hardcoded in `alembic.ini`.

The `env.py` imports all models via the `models` package, enabling future
`--autogenerate` usage once a live PostgreSQL connection is available.

## Current Limitations

- **No live PostgreSQL connection is required** — the migration was written by
  hand and verified syntactically, but has not been executed against a running
  database in this milestone.
- **`updated_at` is not auto-updated** — the `ON UPDATE` trigger must be added
  via a PostgreSQL function or handled at the application layer in a future
  milestone.
- **JSONB GIN indexes** are not created yet. They become relevant when the
  Event Processor begins querying `payload` fields. Add them in a future
  migration once query patterns are known.
- **No repository or service layer** — the table exists but nothing can write
  to it from application code yet.
- **SQLite remains the dev database** — the existing application still boots
  with SQLite. PostgreSQL is only targeted by this migration. Developers must
  update `DATABASE_URL` in `.env` when using a local PostgreSQL instance.
