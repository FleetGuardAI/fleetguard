# Milestone 9 — Verification Decision Engine

---

## Overview

This milestone documents the **Verification Decision Engine** component of the
Validation & Enrichment Engine (VEE). 

Note: The code for this engine was implemented during the Validation Framework
milestone under the class name `ValidationEngine`. This document serves to 
explain its specific role as the orchestrator and decision-maker for the validation pipeline.

The Verification Decision Engine coordinates all registered validators, executes 
only those that apply to a given event, aggregates their results, and produces a 
single, final `VerificationStatus` that is written back to the event store. It contains 
**no validation logic itself**.

---

## Architecture

The engine implements the `EventSubscriber` interface and is registered with the 
`EventDispatcher`. 

When an event is published, the Decision Engine performs the following pipeline:

1. **Context Creation:** Wraps the `OperationalEventResponse` in an immutable `ValidationContext`.
2. **Discovery:** Iterates through its internal registry of `BaseValidator` instances.
3. **Applicability Check:** Calls `applies_to(context)` on each validator. Validators returning `False` are silently skipped.
4. **Execution:** Calls `validate(context)` on applicable validators.
5. **Aggregation:** Collects all `ValidationResult` objects and applies Decision Rules to determine the final status.
6. **Persistence:** Opens a short-lived database session (via `async_session_factory`), updates the event metadata with execution summaries and enrichment data, and advances the event's `verification_status`.

---

## Decision Rules (Result Aggregator)

The engine aggregates multiple `ValidationResult` outcomes into a single `VerificationStatus` 
using a strict, hardcoded priority order. 

| Priority | Rule | Final Status |
|---|---|---|
| 1 | If **ANY** validator returns `REJECTED` | `REJECTED` |
| 2 | If **ANY** validator returns `NEEDS_MANUAL_REVIEW` | `DISPUTED` |
| 3 | If **ANY** validator returns `PENDING_MORE_DATA` | `PENDING` |
| 4 | If **ALL** applicable validators return `VERIFIED` | `VERIFIED` |
| 5 | If no validators ran (fallback) | `PENDING` |

**Conflict Resolution:**
If validators disagree (e.g., Validator A returns `VERIFIED` but Validator B returns `NEEDS_MANUAL_REVIEW`), the highest priority rule wins. In this case, Rule 2 dominates Rule 4, so the overall status becomes `DISPUTED`.

---

## Execution Summary & Enrichment

The engine produces detailed output for auditing and debugging. All data is nested within the `event_metadata["vee"]` block of the persisted event.

- **Execution Summary:** Logs which validators ran, their individual outcomes, reasons, and warnings.
- **Enrichment Data:** Any contextual data generated by validators is merged under a namespace corresponding to the `validator_name` to prevent collisions.

**Example Persisted Metadata:**
```json
{
  "vee": {
    "validation_summary": {
      "validators_run": ["fuel_structural_validator"],
      "outcomes": {
        "fuel_structural_validator": "VERIFIED"
      },
      "all_reasons": {},
      "all_warnings": {},
      "final_status": "VERIFIED"
    }
  }
}
```

## Current Limitations

- **Hardcoded Rules:** The aggregation rules are currently hardcoded in Python. In the future, these rules might need to be configurable per tenant or per event type.
- **Synchronous Execution:** The engine currently awaits each validator sequentially (`for validator in self._validators:`). For I/O heavy validators (like external API calls), this could be optimized using `asyncio.gather` for concurrent execution.
- **No Dependency Graph:** The engine assumes validators can run in any order. It does not currently support scenarios where Validator B requires enrichment output from Validator A.

---

## Future Enhancements

- **Concurrent Execution:** Update `_run_validators` to execute applicable validators concurrently using `asyncio.gather` to reduce overall validation latency.
- **Configurable Decision Models:** Allow fleet managers to customize the aggregation rules (e.g., treating certain warnings as `DISPUTED` instead of `VERIFIED`).
- **Data Pre-fetching:** Implement a mechanism to pre-populate `ValidationContext.extra` with historical data (e.g., average fuel prices) before passing the context to validators, reducing duplicate DB queries.
