# Epic — Evidence Store

---

## Overview

The **Evidence Store** is a core pillar of the **Evidence Framework Epic**. It formalizes the concept of "Evidence" as a first-class business entity within FleetGuard.

Evidence records provide the raw facts supporting an **Operational Event**. They are generated by downstream systems—such as OCR engines processing documents, Telematics gateways parsing GPS pings, or manual data entry by fleet managers. 

By detaching evidence generation from the event capture layer, the system can asyncronously accumulate evidence for an event over time, enabling the Validation Engine to make highly informed trust decisions.

---

## Domain Model

**Evidence** (`backend/models/evidence.py`)
- **Immutability**: Once an evidence record is generated and marked `COMPLETED` (or `FAILED`), it can never be changed. Corrections are handled by appending new evidence records.
- **Data Structure**: Designed with a schema-less `raw_data` JSON payload. This allows FleetGuard to ingest completely new types of evidence (like a new IoT sensor) without migrating the database schema.

### Core Fields

- `id`: Unique identifier (UUID).
- `event_id`: Foreign key securely linking the evidence to a specific `OperationalEvent`.
- `evidence_type`: Classification enum (e.g., `RECEIPT_DOCUMENT`, `OCR_EXTRACTION`, `GPS_LOCATION`).
- `source`: The identity of the system or user that provided the evidence.
- `status`: Lifecycle state (`PENDING`, `COMPLETED`, `FAILED`).
- `raw_data`: The actual facts (e.g., `{"lat": 45.1, "lng": -75.2}`).

---

## Relationships

- **Operational Events own Evidence**: An Operational Event has a one-to-many relationship with Evidence. 
- **Documents are Infrastructure**: A Document is a physical file. Evidence may contain a reference to a Document (e.g., `RECEIPT_DOCUMENT` evidence might have `{"document_id": "123"}` in its `raw_data`), but the Document itself does not contain evidence.

---

## Evidence Lifecycle

1. **Generation Triggered**: A downstream system (e.g., OCR webhook) begins processing a document attached to an event.
2. **Pending State**: The system *may* create a `PENDING` evidence record to indicate that data is being generated.
3. **Completion**: The system posts the finalized facts to `POST /api/v1/events/{event_id}/evidence`. The record is permanently saved as `COMPLETED`.
4. **Validation Consumption**: The Validation Engine reads all attached evidence to score the Operational Event.

---

## Storage Strategy

Evidence is stored in PostgreSQL alongside the Operational Events. The `raw_data` column utilizes PostgreSQL's `JSONB` type in production (or generic `JSON` in SQLite during local development) to allow for high-performance indexing and querying of the schemaless evidence facts by the future Finding Engine.

---

## Future Integrations

This infrastructure lays the groundwork for:
- **Validation Engine**: Will consume evidence to automatically verify or reject events.
- **Fleet Memory**: Will utilize historical evidence to build profiles of drivers and vehicles.
- **Finding Engine**: Will query the `raw_data` payloads to discover anomalies.
- **Digital Twins**: Will use the evidence streams to update the virtual state of trucks in real-time.
